2. Remaining Performance Items — Do They Still Remain?
§1.5 — MACE buy-affordability per-stock Python loop
for stock_idx in range(self.stock_dim):
    stock_shares = buy_shares[:, stock_idx]
    stock_total = requested_buy_total[:, stock_idx]
    can_buy = (stock_shares > 0) & (stock_total <= available_cash)
    accepted_buy_shares[can_buy, stock_idx] = stock_shares[can_buy]
    available_cash[can_buy] -= stock_total[can_buy]
Python
Keep as-is. The scalar env iterates stocks in index order and short-circuits on the running cash balance — exactly what this loop reproduces. The test test_mace_scalar_vec_single_env_parity and test_mace_multistep_permanent_impact_and_path_parity rely on this ordering, and any fully-vectorised alternative (scale-down, greedy-by-cost, …) changes the acceptance semantics and would break those tests.

Cost quantification. At stock_dim=100, num_envs=2048, one kernel-launch-per-stock per step costs ~100 launches × ~5–10 µs = ~0.5–1 ms per step of CUDA launch overhead. On a typical 252-step training episode this is ~0.25 s per env reset — well under 1 % of end-to-end training time for a PPO run with repeat_times=16. Not worth breaking parity over.

Low-risk future optimisation (no parity break): wrap the loop in @torch.jit.script:

@th.jit.script
def _sequential_affordability(buy_shares, requested_buy_total, cash):
    num_envs, stock_dim = buy_shares.shape
    accepted = th.zeros_like(buy_shares)
    available = cash.clone()
    for i in range(stock_dim):
        can_buy = (buy_shares[:, i] > 0) & (requested_buy_total[:, i] <= available)
        accepted[:, i] = th.where(can_buy, buy_shares[:, i], th.zeros_like(buy_shares[:, i]))
        available = available - th.where(can_buy, requested_buy_total[:, i], th.zeros_like(available))
    return accepted
Python
TorchScript fuses the per-iteration kernel launches into a single compiled graph. Preserves semantics exactly (same scalar parity tests pass), drops launch overhead to ~O(1) per step. Recommended as a future PR — one function, one test to confirm parity with the current loop.

Margin per-stock loop in step() (originally tagged in §3 of audit #1)
for stock_idx in stock_order:
    if (trade_shares[:, stock_idx] < 0).any():
        trade_value, trade_cost, trade_sides, aggregate_rows = self._execute_sell_direction(...)
Python
Keep as-is. The position-flipping semantics (cover-short→buy-long, sell-long→open-short) have genuine per-stock state dependence (each helper mutates self.stocks, self.long_cash, self.short_limit, etc., and later helpers observe the mutation). This is fundamentally serial per stock, and test_margin_scalar_vec_single_env_parity locks it in.

Cost quantification. Worse than MACE because each stock fires up to 4 kernel-launching helpers (_sell_long, _sell_short, _cover_short, _buy_long, plus one apply_trade and a maintenance check each). At stock_dim=100 the launch overhead is the dominant cost of Margin step when num_envs is small. On large num_envs (≥1024) the per-kernel work dominates and the overhead ratio drops below 5 %.

Recommended optimisation path (if Margin throughput becomes a bottleneck):

Split trades into four disjoint per-stock groups before the loop:
long_cover_group (buy when current stock < 0)
long_buy_group (buy when current stock ≥ 0)
short_sell_long_group (sell when current stock > 0)
short_open_group (sell when current stock ≤ 0)
Run one batched apply_trades_batched per group in the canonical stock order (sell-then-buy).
Apply a single batched affordability mask per group (like MACE does now for buys).
This is a ~200-line refactor and still preserves scalar parity as long as the four groups are applied in the same sequence as the scalar env. Out of scope for this review; flagged for a follow-up PR if profiling shows Margin step() as the hot path.
